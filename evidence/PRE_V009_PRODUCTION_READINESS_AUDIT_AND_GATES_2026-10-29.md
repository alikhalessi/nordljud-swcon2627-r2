## 2. Production-ready definition for this research deliverable

**Target:** a **controlled, reproducible public pilot / production-quality release candidate**, not a promise of unlimited scale, flawless linguistic correctness, clinical-grade security, a native Android app or a validated cognitive-science intervention.

A Vibe build may be marked `READY_TO_FREEZE` **only if all release-blocking gates below are evidenced**:

1. **R01 Release engineering / reproducibility:** exact dependency lockfile; CI tests/typecheck/production build pass from a clean environment; RED commits cannot be automatically promoted to public Production; preview or candidate deployment for QA; rollback path identified. Distinguish green CI from live deployment health.
2. **R02 Authentication / Cloud and data security:** Guest experience; successful Google OAuth and supported email sign-in/registration; correct redirects, sign-out/session expiry; all existing Favorites/Studied/Practice History survive. V-008 user-owned tables deployed **only after separate explicit Production migration authorization**, with actual same-user CRUD, cross-account isolation denial, anon-denial, and no guest-to-account silent merge. If migration is not authorized, **production readiness of the full V-008 specification is BLOCKED**.
3. **R03 E2E / UX / accessibility / resilience:** automated browser tests and hands-on UAT for dates, timezones (including local rollover and DST), all four levels, daily/archive/quiz, exact multi-meaning `sticka`, speech unsupported cases, guest offline-storage unavailable, clear-data, refresh, keyboard/screen-reader basics and narrow viewport. Record reproducible defects; no forced PASS. Test DB negative cases with non-sensitive test identities.
4. **V-009 final acceptance and freeze:** no open P0/P1, all agreed P2 either closed or explicitly signed off in a limitations register; production build same SHA tested and accepted; actual deploy, auth, storage, privacy, recovery, monitoring and release controls verified; evidence reproducible. Student explicitly accepts final release; create immutable tag / release SHA, product manifest, access URL and runbook. Then forbid further `condition/vibe` feature changes, start SDD from neutral baseline and requirements only.
5. **Research integrity:** preserve AI draft → exact student approval → RED/GREEN → human acceptance for each corrective iteration; maintain source/baseline/commit timestamps and user-origin scope change disclosure. Never use CI failure count as causal evidence of method superiority by itself.
